# SPEC — Item 16 — Canal de notificação secundário

> Contexto e regras comuns: consultar [00-contexto-e-regras.md](00-contexto-e-regras.md).

## Canal de notificação secundário

**Problema**: todo o alerting crítico (kill switch, riscos, rollback
Fase 3) passa só pelo Telegram. Se a API do Telegram tiver uma falha, ou a
conta/bot for limitada/banida, não há nenhum alerta — nem sequer se sabe que
algo correu mal, porque o próprio canal de aviso é o que falhou.

**Objetivo**: adicionar um canal secundário (ex.: email via SMTP) pelo menos
para os eventos `risk`/`kill_switch` — não é preciso duplicar todo o ruído
de notificações, só os eventos que exigem atenção imediata.

**Critério de aceitação**: evento `risk`/`kill_switch` simulado e confirmado
que chega pelos dois canais; falha simulada do canal Telegram (ex.: token
inválido) e confirmado que o canal secundário continua a funcionar.
